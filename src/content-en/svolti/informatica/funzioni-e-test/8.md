## Exercise 1

Find the result of `report()` with assertions enabled and with `NDEBUG` defined when `<assert.h>` is included. Rewrite the body so that both configurations yield the result of the first.
```c
#include <assert.h>

int report(void)
{
    int n = 7;
    assert(--n >= 0);
    return n;
}
```

With assertions enabled the result is $6$. With assertions disabled it is $7$. The corrected body executes, in order, `int n = 7;`, `--n;`, `assert(n >= 0);` and `return n;`.

<div class="spiegazione">

In the first case the assertion argument is evaluated. The `--` operator decrements `n` before the comparison and $6$ satisfies the condition. In the second case the macro removes evaluation of its argument. The return therefore gives the value set during initialization.

To check the rewrite, examine the statements that modify `n`. Initialization assigns $7$ and the following statement changes it to $6$, regardless of the macro. The rewritten assertion reads `n`, so its presence affects only the check.

</div>

## Exercise 2

The specification of `rating` accepts scores of at least $18$, returning $1$ for such a score and $0$ otherwise. The program implements the oracle with two comparisons in `main`. Find its exit status and explain the effect of correcting the condition.
```c
#include <stdlib.h>

int rating(int score)
{
    return score > 18;
}

int main(void)
{
    if (rating(17) != 0) {
        return EXIT_FAILURE;
    }
    if (rating(18) != 1) {
        return EXIT_FAILURE;
    }
    return EXIT_SUCCESS;
}
```

The check at $17$ passes. At $18$ the code returns $0$ and the expected value is $1$. The program therefore exits with `EXIT_FAILURE`. Replacing `score > 18` with `score >= 18` makes both checks pass and produces `EXIT_SUCCESS`.

<div class="spiegazione">

The expected results come from the specification, so they can be calculated before reading the function. A score of $17$ is below the requirement. A score of $18$ meets it exactly. In the body shown, the strict comparison makes $18$ produce $0$ as well, so the second check reports the defect.

Check the correction by evaluating `17 >= 18` and `18 >= 18` separately. They give $0$ and $1$. Both checks in `main` are ordinary `if` statements. The macro `NDEBUG` affects `assert`, so these checks also run in a build that defines it.

</div>

## Exercise 3

The following program tests a function with state. Find the output with assertions enabled and with `NDEBUG` defined before `<assert.h>` is included. Rewrite `main` so that both configurations execute the same calls and print the same values.
```c
#include <assert.h>
#include <stdio.h>

int next_ticket(void)
{
    static int last = 100;
    last += 2;
    return last;
}

int main(void)
{
    assert(next_ticket() == 102);
    assert(next_ticket() > 102);
    printf("%d\n", next_ticket());
    return 0;
}
```

| Configuration | Calls of `next_ticket` | Output |
| --- | --- | --- |
| Assertions enabled | $3$ | `106` |
| `NDEBUG` defined | $1$ | `102` |

In the following version the calls are outside the assertions.

```c
int main(void)
{
    int first = next_ticket();
    assert(first == 102);
    int second = next_ticket();
    assert(second > 102);
    printf("%d %d %d\n", first, second, next_ticket());
    return 0;
}
```

In both configurations the rewritten version prints `102 104 106`.

<div class="spiegazione">

The variable `last` has static storage duration, so each call starts from the value left by the previous one and increases it by $2$. With assertions enabled the macro evaluates its argument. The first assertion receives $102$ and the second receives $104$, which satisfies $104>102$, so the call inside `printf` is the third and returns $106$. With `NDEBUG` defined the two assertions expand to expressions without effect and the calls written in their arguments are not executed. The call inside `printf` is then the first and returns $102$.

With assertions enabled the program passes both checks and still prints a value different from the one of the build with `NDEBUG`, because the calls inside `assert` modify `last`. In the rewrite each call initializes a variable and the assertions only read `first` and `second`. The three calls therefore take place in both configurations, in the same order. Printing `first` and `second` uses both variables also with `NDEBUG`, so GCC does not issue the unused-variable warning.

</div>
