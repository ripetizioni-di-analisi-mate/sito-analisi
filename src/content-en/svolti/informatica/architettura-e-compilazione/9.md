## Exercise 1

The following program runs on a little-endian machine with eight-bit bytes and $32$-bit `unsigned`. Determine the exact output. Then give the output on a big-endian machine with the same types.
```c
#include <stdio.h>

int main(void)
{
    unsigned x = 0x0A0B0C0Du;
    const unsigned char *p = (const unsigned char *)&x;

    for (size_t i = 0; i < sizeof x; ++i) {
        printf("%zu %02x\n", i, (unsigned)p[i]);
    }
    return 0;
}
```

On the little-endian machine the program prints

```text
0 0d
1 0c
2 0b
3 0a
```

On the big-endian machine it prints

```text
0 0a
1 0b
2 0c
3 0d
```

<div class="spiegazione">

The pointer `p` holds the address of the first byte of `x`, so `p[i]` designates the byte with index $i$ of the representation. C allows the representation of any object to be read through an lvalue of character type, so these reads have defined behavior. By the hypothesis on the types `sizeof x` equals $4$, so the loop examines the four bytes in address order.

In **little-endian** order the byte with index $0$ is the least significant, namely `0x0D`. The other bytes follow with increasing weight. In big-endian order the byte with index $0$ is the most significant, so the byte values appear in reverse order. The value of `x` is the same on both machines and only the arrangement of its bytes changes.

The conversion `%02x` writes at least two lowercase hexadecimal digits and pads with a leading zero, so `0x0D` appears as `0d`. The cast gives the argument the type `unsigned int` required by `%x`, while `%zu` matches the type `size_t` of `i`.

</div>

## Exercise 2

Determine the value printed by the following program on a little-endian machine and on a big-endian machine, both with eight-bit bytes and $32$-bit `unsigned` without padding bits.
```c
#include <stdio.h>
#include <string.h>

int main(void)
{
    const unsigned char bytes[4] = {0x01, 0x02, 0x00, 0x00};
    unsigned value;

    memcpy(&value, bytes, sizeof value);
    printf("%u\n", value);
    return 0;
}
```

$$
\begin{aligned}
\text{little endian} &= 1\cdot256^0+2\cdot256^1=1+512=513\\[6pt]
\text{big endian} &= 1\cdot256^3+2\cdot256^2=16777216+131072=16908288 .
\end{aligned}
$$

The program prints `513` on the little-endian machine and `16908288` on the big-endian machine.

<div class="spiegazione">

`memcpy` copies `sizeof value` bytes, that is four, from the array to the object `value`, preserving address order. The copy transfers bytes without any conversion, so byte `0x01` occupies index $0$ of the representation of `value` on both machines. The value therefore depends on the weight that the byte order assigns to each index.

On the little-endian machine index $0$ has weight $256^0$ and index $1$ has weight $256^1$. On the big-endian machine the same indices have weights $256^3$ and $256^2$. The two zero bytes contribute nothing in either case.

The variable `value` is declared without an initial value. The call to `memcpy` writes all four of its bytes before `printf` receives its value. Since `unsigned` has $32$ value bits and no padding bits, every pattern of the four bytes represents a valid value and the read is defined.

</div>

## Exercise 3

The function `read_le32` must return the unsigned word stored in little-endian order in the four bytes pointed to by `b`, on any machine with eight-bit bytes and $32$-bit `int` and `unsigned`. The test program uses the bytes `0x78`, `0x56`, `0x34` and `0xF2`. Find the error in the function, correct it with the smallest change and give the output of the corrected program.
```c
#include <stdio.h>

unsigned read_le32(const unsigned char *b)
{
    return b[0] | b[1] << 8 | b[2] << 16 | b[3] << 24;
}

int main(void)
{
    const unsigned char data[4] = {0x78, 0x56, 0x34, 0xF2};

    printf("%x\n", read_le32(data));
    return 0;
}
```

$$
242\cdot2^{24}=4060086272>2^{31}-1=2147483647 .
$$

The term `b[3] << 24` has undefined behavior. The corrected function is

```c
unsigned read_le32(const unsigned char *b)
{
    return b[0] | b[1] << 8 | b[2] << 16 | (unsigned)b[3] << 24;
}
```

| Term | Value |
|---|---|
| `b[0]` | `0x00000078` |
| `b[1] << 8` | `0x00005600` |
| `b[2] << 16` | `0x00340000` |
| `(unsigned)b[3] << 24` | `0xF2000000` |

The corrected program prints `f2345678`.

<div class="spiegazione">

Each `b[i]` has type `unsigned char`. The operands of `<<` undergo the **integer promotions**, and since `int` represents all values from $0$ to $255$, `b[3]` is converted to `int`. A left shift of a non-negative `int` is defined only when the result is representable in `int`. The product $242\cdot2^{24}$ exceeds the maximum `INT_MAX`, so the expression has **undefined behavior**. With `-fsanitize=undefined` GCC reports it at run time as a shift of $242$ by $24$ places that cannot be represented in `int`, even though the printed output matches the expected value.

The cast gives `b[3]` the type `unsigned int`, which the promotions leave unchanged. A shift of an `unsigned` by fewer than $32$ places is always defined, and here the result `0xF2000000` is representable. The other terms have results representable in `int`, because the largest, `b[2] << 16`, does not exceed $255\cdot2^{16}=16711680$. In the `|` operator the usual arithmetic conversions bring the non-negative `int` operands to `unsigned` with the same value. The function uses only the byte values and arithmetic weights, so the result is the same on little-endian and big-endian machines.

</div>
